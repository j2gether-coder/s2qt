## 1. 8/29안 대비 무엇이 좋아지는가

### 1-1. Step2 저장 시 유실 문제가 사라진다 (8/29안 3-3)

8/29안의 **유일한 위험 지점**이었습니다. `QTStep2Service.Save()`는 `QTSectionDoc`을 새로 조립해 통째로 덮어쓰므로([qtstep2_service.go:182-240](../service/qtstep2_service.go#L182-L240)), temp.json에 실린 `infographic`은 Step2 저장 한 번에 100% 소실됩니다. 그래서 `preserveInternalBlogFields` 패턴을 복제한 round-trip 보존이 **필수**였습니다.

새 설계에서는 **temp.json에 `infographic`을 넣지 않습니다.** infographic.md가 Step1에서 이미 파일로 떨어졌고 원본 JSON은 DB에 있으므로, temp.json이 QT 4개 섹션만 담아도 아무것도 잃지 않습니다.

> 작업지시서의 "temp.json은 버전 1.0으로 저장하여 step2에서 검토 및 편집을 수정하지 않도록 한다"를 **"LLM이 준 v1.1 JSON에서 QT 부분만 떼어 기존 v1.0 스키마로 temp.json에 쓴다"** 로 해석했습니다. 이 해석이면 `QTStep2Service`의 Load/Save는 **한 줄도 바꾸지 않습니다.** `Save()`가 이미 `Version: "1.0"`을 하드코딩하고 있어([qtstep2_service.go:183](../service/qtstep2_service.go#L183)) 버전 표기도 저절로 정합합니다. **2026-08-30 확정** — `1.0`은 현행 버전, `1.1`은 인포그래픽 추가 버전입니다 (7장 결정 1).

**작업 3번(round-trip 보존, 0.5일) 통째로 제거.**

### 1-2. Step3 3중 게이트가 사라진다 (8/29안 5-1)

8/29안은 "Step3 재실행이 사용자의 md 편집본을 덮어쓴다"를 막기 위해 `adult` + `infographic 존재` + `파일이 없거나 0바이트`의 3중 게이트, `isEmptyOrMissing()` 헬퍼, `MakeInfographic` 강제 재생성 플래그, Step3 체크박스, `os.Truncate` 정리 로직을 전부 요구했습니다.

새 설계에서는 **생성 시점이 "사용자가 결과저장 버튼을 누른 순간" 하나뿐**입니다. 사용자가 명시적으로 누른 행위이므로 덮어쓰기가 자연스럽고, 재생성도 "Step1에서 다시 저장"으로 끝납니다. Step3를 PDF/PNG 때문에 몇 번 돌리든 md는 건드려지지 않습니다.

**작업 6번(3중 게이트 + 플래그 + 체크박스, 0.5일) 통째로 제거.**

### 1-3. 재작업에서도 인포그래픽이 복원된다 (8/29안 5-4 정면 해결)

8/29안은 재작업 시 인포그래픽을 **포기**했습니다. 근거는 "인포그래픽을 만들려면 전사문이 필요한데 작업내역에 전사문이 저장되지 않는다"였습니다.

새 설계는 md를 **전사문이 아니라 저장된 JSON에서 렌더**하므로 이 제약이 사라집니다. 전사문 저장(설교 1건당 수만 자) 없이 재작업에서 인포그래픽이 그대로 복원됩니다. **8/29안이 "이번 범위에서 제외"한 기능을 공짜로 얻습니다.**

### 1-4. 정리

| 8/29안이 필요로 했던 방어 | 새 설계 |
|---|---|
| Step2 round-trip 보존 | **불필요** |
| Step3 3중 게이트 + `isEmptyOrMissing()` | **불필요** |
| `MakeInfographic` 재생성 플래그 + 체크박스 | **불필요** |
| 새 작업/재작업 진입 시 0바이트화 | **1곳만** (Step1 저장 시 항상 truncate 후 조건부 write) |
| `version` 1.0/1.1 판별로 "재작업 vs LLM 누락" 구분 | **불필요** — 저장 시점에 판정이 끝남 |
| 재작업 시 인포그래픽 미생성 | **복원됨** |

## 2. 새 설계의 데이터 흐름

```
[Step1 결과저장 — 장년]
  LLM 응답(v1.1)
    ├─ 검증 (JSON 유효 + 필드 단위 검증)
    ├─ DB   : 원본 JSON 전문 그대로 보관        ← 재작업의 유일한 원천
    ├─ temp.json      : QT 부분만 v1.0 스키마로  ← Step2 편집 대상
    └─ infographic.md : infographic 부분 렌더    ← 최종 산출물(외부 편집)

[Step2] temp.json 로드 → 편집 → 저장(v1.0) → temp.html    (코드 변경 없음)

[Step3] temp.html → PDF / PNG,  temp.json → blog.html      (infographic 로직 제거)

[작업내역 재작업]
  DB 원본 JSON → temp.json(v1.0) + infographic.md 재생성 → Step2 진입
```

`sections[]`와 `metadata`를 건드리지 않는다는 8/29안 3-2의 원칙은 그대로 유지되므로, **HTML/PDF/PNG/DOCX/PPTX/blog 렌더링 경로의 영향은 여전히 0입니다.**

## 3. 반드시 처리해야 할 함정 7건

### 함정 1 — `SaveManualLLMResult`가 DB 저장에 필요한 값을 받지 못한다

현재 시그니처는 JSON 문자열 하나입니다.

[app.go:550](../app.go#L550)
```go
func (a *App) SaveManualLLMResult(jsonText string) error
```

그런데 `SaveHistory`는 title / bibleText / audience가 **비어 있으면 거부**하고([history_service.go:106-111](../service/history_service.go#L106-L111)), `history_master.title` / `bible_text`는 **NOT NULL**입니다([db_service.go:81-91](../service/db_service.go#L81-L91)). audience도 `history_qt_json`의 필수 컬럼입니다.

LLM이 준 JSON의 `metadata`에서 뽑아 쓸 수도 있지만, **그 값은 신뢰할 수 없습니다.** 8/29 실측에서 5개 모델 중 3개가 메타데이터를 날조했습니다(무료 Copilot `"홍길동 목사"`, **유료 Claude** `"김신일 목사"` / `"하늘가족교회"` / `https://youtu.be/example`).

**대응**: `SaveManualLLMResult(req)`로 확장해 `audience` + 화면 기본정보(`appState.source.basicInfo`)를 함께 받습니다. 프론트에는 이미 `buildLLMRequest()`가 같은 값을 조립하고 있으므로([bindQTStep1.js:14-28](../frontend/src/components/qt/bindQTStep1.js#L14-L28)) 그대로 재사용하면 됩니다. **함정 5도 이 한 번의 확장으로 같이 해결됩니다.**

#### 필수 항목은 제목·본문 성구 둘뿐이며, 이미 3중으로 일치한다 (2026-08-30 확인)

이 프로젝트의 필수 입력 규칙은 세 계층에서 **정확히 같은 집합**을 가리킵니다.

| 계층 | 필수 | 선택(빈 값 허용) |
|---|---|---|
| 화면 — [mainWorkspace.js:435-462](../frontend/src/components/mainWorkspace.js#L435-L462) | 제목, 본문 성구 (`required-mark`) | 찬송, 설교자, 교회명, 설교일 |
| 백엔드 — [app.go:527-541](../app.go#L527-L541), [pipeline_service.go:332-340](../service/pipeline_service.go#L332-L340) | title, bibleText, audience | 나머지 전부 |
| DB — [db_service.go:81-91](../service/db_service.go#L81-L91) | `title` NOT NULL, `bible_text` NOT NULL | `hymn`, `preacher`, `church_name`, `sermon_date` |

**DB가 요구하는 필수 집합 = Step1이 이미 보장하는 집합**이므로, 이 함정의 실질 난이도는 처음 평가보다 **낮습니다.** 넘길 값 중 비어 있을 수 있는 것은 전부 nullable 컬럼으로만 들어가고, `audience`는 화면 진입 자체가 연령대 선택으로 이뤄지므로 항상 존재합니다. 남는 작업은 시그니처 확장 하나뿐입니다.

infographic.md도 마찬가지입니다. 렌더에 필요한 메타는 `# 제목`과 `## 성경본문` **두 개뿐**이고 이는 정확히 필수 항목과 일치하므로, 함정 5의 대응(화면 기본정보 우선)에서 값이 비어 빈 문서가 나올 여지가 없습니다.

#### 다만 결과저장 버튼은 필수값을 재검증하지 않는다

필수값 검증은 **프롬프트 생성 시점**에만 걸립니다. 결과저장 핸들러는 JSON 문자열이 비었는지만 봅니다.

[bindQTStep1.js:96-105](../frontend/src/components/qt/bindQTStep1.js#L96-L105)
```js
const jsonText = resultBox?.value || '';
if (!jsonText.trim()) { ... return; }
await SaveManualLLMResult(jsonText);       // 제목/성구는 확인하지 않음
```

지금은 결과저장이 파일 쓰기뿐이라 문제가 없지만, **DB INSERT가 붙는 순간 달라집니다.** 프롬프트를 만들지 않고 JSON만 붙여 넣었거나 프롬프트 생성 후 기본정보를 지운 경우, `SaveHistory`가 영문 메시지(`title and bible text are required`)로 실패하거나 NOT NULL 제약에 걸립니다. temp.json은 이미 쓰인 뒤라 **부분 저장 상태**가 됩니다.

**대응**: 결과저장 진입부에서 제목·본문 성구를 먼저 확인하고 한국어 안내로 막습니다(방어 코드 수준). 저장 순서도 **검증 → temp.json → infographic.md → DB**로 두어, 실패하더라도 DB에 반쪽 이력이 남지 않게 합니다.

### 함정 2 — 작업내역이 2중으로 쌓인다

이력 저장은 현재 **Step2 저장 버튼 한 곳**에서만 일어납니다.

[bindQTStep2.js:324-325](../frontend/src/components/qt/bindQTStep2.js#L324-L325)
```js
const historyReq = buildHistoryPayload(audienceId, step2Payload);
const historyId = await SaveHistory(historyReq);
```

`SaveHistory()`는 호출될 때마다 `history_master` **새 행 + `history_qt_json` 새 행**을 INSERT합니다([history_service.go:121-139](../service/history_service.go#L121-L139)). 여기에 Step1 저장이 추가되면 설교 1건에 목록 행이 **2개** 생깁니다.

> 작업내역이 INSERT-only 스냅샷 설계라는 점은 확인했습니다. 다만 지금까지의 중복은 "사용자가 Step2 저장을 여러 번 누른 결과"인 반면, 이번 중복은 **정상 1회 진행에도 항상 2행**이 되는 구조적 중복입니다. 성격이 다릅니다.

**대응 3안** (7장 결정 2)

| 안 | 내용 | 평가 |
|---|---|---|
| (a) | Step1이 `history_master` + 신규 `history_llm_json` 행을 만들고 historyId를 `appState`에 보관 → Step2 저장은 **같은 master에** `history_qt_json`만 추가 | 목록 1행 유지, 원본과 편집본이 한 건에 묶임. 다만 한 건에 두 포맷이 공존해 조회 우선순위를 코드로 정해야 함 |
| (b) | Step1/Step2 둘 다 새 master 생성 | 구현 최소. 목록이 2배로 불어남 |
| **(c)** | **Step1에서만 저장하고 Step2 이력 저장 폐지** | **채택 (2026-08-30 결정).** 아래 참조 |

#### 결정 — (c) DB 저장은 Step1에서만 한다 (2026-08-30)

이 결정으로 **함정 2와 함정 6이 동시에 사라지고, 7장의 열린 결정 3개가 1개로 줄어듭니다.**

**얻는 것**

1. **이력 1건 = 목록 1행.** 이중화 문제가 원천 소멸합니다.
2. **결정 3(재작업 복원 소스)이 자동으로 확정됩니다.** 편집본이 DB에 없으므로 복원 소스는 원본 하나뿐입니다. 이는 작업지시서 원문("step1에서 저장된 JSON을 불러와 temp.json과 infographic.md를 저장한다")과 **정확히 일치**합니다. 8/29 검토에서 권했던 혼합안은 지시서에 없던 것을 덧붙인 것이었으므로 철회합니다.
3. **DB에 담기는 것이 LLM 원본 그대로**가 됩니다. 평면 페이로드로 눌러 담지 않으므로 필드 손실이 구조적으로 없습니다.
4. **기존 버그 하나가 덤으로 고쳐집니다.** `buildQTSectionDocFromFlat()`은 `support_scriptures_full`을 복원하지 않아([history_service.go:559-629](../service/history_service.go#L559-L629)), 지금은 **재작업으로 만든 blog.html에 관련 성구 전체 본문이 빠집니다**([blog_service.go:97-103](../service/blog_service.go#L97-L103)의 폴백 경로). 8/29 검토가 "이번 통합안과 무관한 기존 동작"으로 남겨 둔 항목입니다. 원본 JSON에서 복원하면 이 필드가 그대로 살아 돌아옵니다.
5. **프론트 부작용이 없습니다.** `appState.historySelected`는 [bindQTStep2.js:327](../frontend/src/components/qt/bindQTStep2.js#L327)과 [historyWorkspace.js:528](../frontend/src/components/history/historyWorkspace.js#L528) **두 곳에서 쓰기만 하고 읽는 코드가 어디에도 없습니다.** Step2의 `SaveHistory` 호출을 제거해도 깨지는 곳이 없습니다.

**반드시 함께 처리할 것**

- **구버전 이력 호환.** 기존 DB의 `history_qt_json` 행은 전부 평면 포맷입니다. 평면 복원 경로(`parseFlatQTStep2JSON` / `buildQTSectionDocFromFlat`)를 **읽기 전용으로 남겨야** 지금까지 쌓인 작업내역을 계속 재작업할 수 있습니다. **테이블은 기존 `history_qt_json`을 그대로 쓰고**, 재작업은 뽑은 1행에 `sections` 배열이 있는지로 **"원본 경로 / 평면 경로"** 를 가릅니다. 스키마 변경은 없습니다 (함정 3·4).

**수용해야 할 변화 3가지**

| # | 변화 | 평가 |
|---|---|---|
| 1 | **이력의 의미가 "완료한 작업" → "LLM 결과를 받은 작업"** 으로 바뀝니다. Step2·3을 진행하지 않고 중단해도 목록에 남습니다 | 수용 가능. 현재도 Step3 미실행 건이 목록에 남으므로 한 단계 앞당겨질 뿐이고, 중단한 작업을 나중에 이어가는 데는 오히려 유리합니다 |
| 2 | **목록의 제목이 Step1 기본정보로 고정**됩니다. Step2에서 제목을 고쳐도([qtStep2.js:49](../frontend/src/components/qt/qtStep2.js#L49) 편집 가능) `history_master.title`에는 반영되지 않습니다 | 대부분 Step1 제목이 그대로 최종 제목이 되므로 영향이 작습니다. 문제가 되면 Step2 저장 시 `history_master.title`만 UPDATE하는 예외를 두는 방법이 있으나, "Step2는 DB를 쓰지 않는다"는 원칙이 흐려지므로 **일단 두고 실사용에서 판단**하기를 권합니다 |
| 3 | **Step2 편집본은 DB에 남지 않습니다.** 재작업은 항상 LLM 원본에서 다시 시작합니다 | 이제 버그가 아니라 **명시된 설계**입니다. 다만 사용자가 "이어서 편집"을 기대할 수 있으므로 재작업 버튼 근처에 **"LLM 원본에서 다시 시작합니다"** 안내를 두는 편이 좋습니다. 세션을 닫지 않았다면 `var/temp/temp.json`에 마지막 편집본이 그대로 남아 있습니다 |

### 함정 3 — `qt_result_json`에 두 가지 포맷이 섞인다

현재 이 컬럼에는 프론트가 만든 **평면(flat) 페이로드**만 들어갑니다([bindQTStep2.js:194](../frontend/src/components/qt/bindQTStep2.js#L194)). 재작업 복원도 평면 전제로 파싱합니다.

[history_service.go:473-478](../service/history_service.go#L473-L478)
```go
flat, err := parseFlatQTStep2JSON(qtRow.QTResultJSON, audience)
doc := buildQTSectionDocFromFlat(flat, audience)
```

Step1 원본(중첩 v1.1)을 같은 컬럼에 넣으면 `parseFlatQTStep2JSON`이 **조용히 실패**합니다. 중첩 문서의 `title`/`summaryBody`는 `metadata`와 `sections[]` 안에 있어 평면 필드로는 전부 빈 값이 되고, 결국 다음 에러로 끝납니다([history_service.go:548-554](../service/history_service.go#L548-L554)).

```
flat qt result json fields are empty
```

`GetHistoryQTJSON()`은 `ORDER BY updated_at DESC LIMIT 1`로 **가장 최근 1행만** 가져오므로([history_service.go:386-392](../service/history_service.go#L386-L392)), 같은 master에 두 포맷이 섞이면 어느 쪽이 뽑힐지가 저장 순서에 좌우됩니다.

#### 결정 2 채택으로 문제의 성격이 바뀐다 (2026-08-31 재검토)

위 서술은 **"Step2도 DB에 쓴다"는 전제**에서 나온 것입니다. 결정 2로 Step2가 DB를 쓰지 않게 되면서, 두 포맷은 **동시에 공존하지 않고 시간순으로 갈립니다.**

- 옛 이력 = 전부 평면 (과거 Step2 저장분)
- 신규 이력 = 전부 원본 (Step1 저장분)
- `SaveHistory()`가 master와 json 행을 함께 INSERT하고 `UpsertHistoryQTJSON()`은 호출되지 않으므로, **`history_master` 1건당 `history_qt_json` 행은 정확히 1개**입니다

따라서 "어느 행이 뽑힐지"의 모호함이 사라지고, 남는 것은 **뽑은 1행이 어느 포맷인지 가리는 일**뿐입니다.

**대응 — 테이블은 그대로 두고 판별만 한다.** 중첩 문서에는 `sections` 배열이 반드시 있고 평면 페이로드에는 없으므로 확실하게 갈립니다.

```go
var probe struct {
    Sections []json.RawMessage `json:"sections"`
}
_ = json.Unmarshal([]byte(qtRow.QTResultJSON), &probe)

if len(probe.Sections) > 0 {
    // 신규: LLM 원본 → temp.json(v1.0) + infographic.md
} else {
    // 구버전: 기존 평면 경로 (parseFlatQTStep2JSON 유지)
}
```

> **이전 개정에서 권했던 별도 테이블 `history_llm_json` 신설은 철회합니다.** 분리의 근거 두 가지(동시 혼재, 구분 컬럼 추가 필요)가 모두 결정 2로 소멸했는데 결론만 그대로 옮겨 온 것이 원인이었습니다. 분리를 유지하면 오히려 함정 4-1의 부작용 3건을 새로 만들어 냅니다.

### 함정 4 — DB 스키마 마이그레이션 경로가 없다 → **해당 없음**

`InitSQLite()`는 `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`만 실행하며([db_service.go:65-114](../service/db_service.go#L65-L114)), **`ALTER TABLE` 경로가 전혀 없습니다.** 따라서 기존 테이블에 구분 컬럼(`source_stage` 등)을 추가하는 설계는 애초에 불가능합니다.

**함정 3의 대응(테이블 무변경 + 포맷 판별)은 스키마를 전혀 건드리지 않으므로 이 제약에 걸리지 않습니다. `db_service.go`는 수정 대상에서 제외됩니다.**

연령대 역시 **왼편 네비게이션 메뉴에서 정해져** `audience` 컬럼에 그대로 들어가므로, 컬럼을 추가해야 할 지점이 없습니다.

#### 함정 4-1 — 별도 테이블을 택했을 때 새로 생겼을 부작용 3건

분리 안을 철회하는 근거로 남겨 둡니다. 아래는 전부 **"신규 이력에 `history_qt_json` 행이 없다"**에서 파생됩니다.

| 위치 | 분리 시 발생했을 문제 |
|---|---|
| [historyWorkspace.js:81-97](../frontend/src/components/history/historyWorkspace.js#L81-L97) `loadAudienceAvailability()` | `GetHistoryQTJSON`만 조회하므로 신규 이력의 `audienceMap`이 비고, [historyWorkspace.js:508-511](../frontend/src/components/history/historyWorkspace.js#L508-L511)에서 **재작업이 완전히 차단** |

### 함정 5 — infographic.md의 제목/본문이 Step1 시점에 굳는다

md의 제목·성경본문은 metadata에서 옵니다([infographic_service.go:73-87](../service/infographic_service.go#L73-L87)). Step1에서 md를 확정하면 **Step2에서 제목을 고쳐도 md에는 반영되지 않습니다.**

실제로 Step2는 화면 기본정보를 temp.json 값보다 **우선**합니다([bindQTStep2.js:151-154](../frontend/src/components/qt/bindQTStep2.js#L151-L154)). 즉 PDF·PNG·blog에는 사용자가 고친 제목이 실리고, infographic.md에는 LLM이 준(경우에 따라 날조한) 제목이 남는 어긋남이 생깁니다.

**대응**: md 렌더 시 metadata를 **LLM JSON이 아니라 Step1 요청값(화면 기본정보)에서** 취합니다. 함정 1의 시그니처 확장으로 그 값이 이미 백엔드에 들어와 있으므로 추가 작업이 없습니다. md가 쓰는 메타는 제목·성경본문 두 개뿐이고 이는 **필수 입력 항목과 정확히 일치**하므로(함정 1 참조), 빈 값으로 인한 결손은 발생하지 않습니다. Step2에서 제목을 바꾸는 경우는 "Step1에서 다시 저장"으로 안내합니다.

### 함정 6 — 재작업 복원이 Step2 편집본을 버린다 → **해소 (결정으로 흡수)**

작업지시서 그대로면 재작업은 **Step1 원본 JSON**에서 temp.json을 재생성하므로, 이전에 Step2에서 다듬은 문장이 사라지고 LLM 원본으로 되돌아갑니다. 8/29 검토 시점에는 이를 "현행 대비 기능 후퇴"로 보고 혼합안을 권했습니다.

**함정 2의 (c)안 채택으로 이 항목은 결정 사항에 흡수되었습니다.** 편집본이 DB에 저장되지 않으므로 복원 소스가 원본 하나뿐이고, 이는 우연이 아니라 **선택한 설계**입니다. 남는 조치는 "재작업 = LLM 원본에서 다시 시작"을 화면 문구로 알리는 것뿐입니다(함정 2의 수용 변화 3).

### 함정 7 — API 자동 경로가 분리 저장을 우회한다

수동 붙여넣기 외에 **API 직접 호출 경로**가 이미 구현되어 있습니다. 이 경로는 LLM 응답을 **그대로** temp.json에 씁니다.

[pipeline_service.go:355-386](../service/pipeline_service.go#L355-L386)
```go
jsonText, err := llm.GenerateQTJSON(meta)
...
if err := s.saveTempJSON(jsonText); err != nil {   // v1.1 전문이 그대로 들어감
```

이 경로를 그냥 두면 temp.json에 `infographic`이 실린 채 Step2로 넘어가고, Step2 저장에서 소리 없이 사라집니다(1-1에서 없앴다고 한 문제가 이 경로에만 되살아납니다). infographic.md도 만들어지지 않습니다.

**대응**: 분리 저장을 **공용 함수 하나로 뽑아** 수동 경로(`SaveManualLLMResult`)와 API 경로(`RunLLMPrepare`) 양쪽이 함께 타게 합니다. 지금 Step1 저장 로직을 새로 짜는 김에 처리하면 추가 비용이 거의 없습니다.

## 4. 인포그래픽이 없는 경우의 처리

| 상황 | temp.json | infographic.md | Step1 저장 | 화면 |
|---|---|---|---|---|
| adult + `infographic` 정상 | QT만 v1.0 | 생성 | 성공 | 표시 없음 |
| adult + `infographic` 누락/불완전 | QT만 v1.0 | **0바이트로 비움** | 성공 | **표시 없음** (로그만) |

- **인포그래픽 누락은 QT 저장을 막지 않습니다**(8/29 5-2 완화책 2 유지).

#### 검증은 하되 화면에는 표시하지 않는다 (2026-08-30 결정 5)

인포그래픽 상태는 **어느 화면에도 노출하지 않습니다.** 다만 검증 자체는 유지합니다 — 불완전한 `infographic` 객체로 md를 만들면 반쪽 문서가 나가므로, **md를 쓸지 말지 판단하려면 검증이 필요**하기 때문입니다. 결과는 로그로만 남깁니다.

```go
// 화면에는 표시하지 않고 로그로만 남긴다 (결정 5)
LogWarn("step1: infographic 검증 실패 — follow=2개(3~5 필요), core 비어 있음. md를 생성하지 않음")
```

**이 결정으로 8/29 확정 9(필드 단위 검증 메시지 포함)는 철회됩니다.** 메시지 문안 작성과 프론트 표시 작업이 빠집니다.

> **알아 두실 점**: 화면 표시가 없으므로, 인포그래픽이 만들어지지 않았다는 사실은 사용자가 `var/temp/infographic.md`를 열어 **0바이트인 것을 보고서야** 알게 됩니다. 8/29 실측에서 5개 모델 모두 6개 필드를 채웠으므로 빈도는 낮을 것으로 보이며, 로그에 사유가 남으므로 원인 추적도 가능합니다. 실사용에서 "왜 md가 비어 있는지 모르겠다"는 상황이 반복되면 그때 Step1 화면에 한 줄 안내를 추가하는 것으로 충분합니다.

**+0.75일로 얻는 것**: 재작업에서 인포그래픽 복원(8/29안이 포기한 기능), Step2 유실 위험 제거, 검증 실패를 Step3가 아닌 Step1에서 즉시 인지. **값어치가 있는 교환으로 판단합니다.**

## 7. 결정이 필요한 사항

### 확정 (2026-08-30)

| # | 항목 | 결정 |
|---|---|---|
| 1 | **버전 번호의 의미** | **`1.0` = 현행 버전(인포그래픽 없음), `1.1` = 인포그래픽 추가 버전.** temp.json은 QT만 담으므로 항상 `1.0`을 유지한다 (아래 상세) |
| 2 | **이력 저장 구조** | **DB 저장은 Step1에서만 한다. Step2는 DB를 쓰지 않는다.** 저장 대상은 LLM 원본 JSON 전문이며, **기존 `history_qt_json` 테이블을 그대로 사용한다**(스키마 변경 없음). 기존 평면 이력은 **읽기 전용으로 호환 유지** (함정 2·3 상세) |
| 3 | **재작업 복원 소스** | **항상 Step1 원본.** 결정 2의 귀결이며 작업지시서 원문과 일치. 8/29 혼합안 권고는 철회 (함정 6) |

#### 결정 1 상세 — 버전은 "인포그래픽 블록의 유무"와 1:1로 대응한다

| 위치 | version | 내용 |
|---|---|---|
| LLM 출력 — **adult** | **`1.1`** | QT 4개 섹션 + `infographic` 객체 |
| LLM 출력 — young_adult / teen / child | `1.0` | **현행과 완전히 동일** (프롬프트에 인포그래픽 블록을 붙이지 않으므로) |
| `history_llm_json` (DB) | 원본 그대로 | adult면 `1.1`, 그 외 `1.0` |
| **`var/temp/temp.json`** | **항상 `1.0`** | QT 부분만. `QTStep2Service.Save()`가 이미 `Version: "1.0"`을 하드코딩하므로([qtstep2_service.go:183](../service/qtstep2_service.go#L183)) **추가 작업 없이 정합** |

이 정의의 실익 두 가지입니다.

1. **`QTStep2Service`는 한 줄도 바꾸지 않습니다.** Load/Save 모두 현행 v1.0 스키마만 다루고, 8/29안이 요구했던 round-trip 보존도 필요 없습니다.
2. **Step1 검증에 그대로 쓸 수 있습니다.** `audience == "adult"`인데 응답의 version이 `1.1`이 아니면 사용자가 **옛 프롬프트의 결과를 붙여 넣었을 가능성**이 높으므로, "인포그래픽이 포함된 프롬프트로 다시 생성해 주세요"라고 정확히 안내할 수 있습니다.

**구현 시 주의**: 현재 프롬프트는 모든 연령대 공용 스키마 블록에서 `"version": "1.0"`을 예시로 고정하고 있습니다([prompt_qt_json.go:149](../service/prompt_qt_json.go#L149)). adult만 `1.1`로 만들려면 스키마 상수를 연령대별로 쪼개기보다, **adult 전용으로 덧붙이는 인포그래픽 블록 안에서 version을 `1.1`로 덮어쓰라고 한 줄 지시**하는 편이 훨씬 쌉니다. 비장년 프롬프트는 그대로 두면 출력이 지금과 100% 동일하게 유지됩니다.

> 참고: 이후 `temp.json`의 version만 보고는 인포그래픽 유무를 알 수 없습니다(항상 `1.0`). 이는 의도된 것으로, temp.json은 **QT 편집 전용 작업 파일**이고 인포그래픽의 소재는 `infographic.md` 파일과 DB 원본이 답합니다. 8/29안이 필요로 했던 "version으로 재작업 vs LLM 누락을 구분"하는 로직은 검증이 Step1로 앞당겨지면서 **불필요해졌습니다.**

| 4 | **Step3 화면의 인포그래픽 표시** | **표시하지 않는다.** `QTStep3Result.Infographic`과 `appState.output.infographicFile`을 제거한다 (5장) |
| 5 | **인포그래픽 검증 실패 시** | **화면에 표시하지 않는다.** QT 저장은 정상 진행하고, 검증 결과는 **로그로만** 남긴다. md는 생성하지 않고 0바이트로 둔다 (4장) |
