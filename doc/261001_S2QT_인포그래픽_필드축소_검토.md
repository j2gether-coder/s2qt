# 261001 · infographic 필드 축소 + QT 섹션 재활용 — 검토

> **READ ONLY 검토서**입니다. 코드는 한 줄도 바꾸지 않았습니다.
> 참조: [파일맵](260922_S2QT_파일맵.md)

## 1. 제안

장년 v1.1 JSON에서 infographic을 `follow` / `extra` / `core` 3개로 줄이고,
`sermon_summary.md`를 조립할 때 나머지를 QT 섹션에서 가져옵니다.

| md 섹션 | 지금 | 제안 |
|---|---|---|
| 말씀의 길잡이 | `infographic.guide` | ← `sections[summary]` |
| 오늘의 적용 | `infographic.apply` | ← `sections[reflection]` |
| 오늘의 기도 | `infographic.prayer` | ← `sections[prayer]` |

---

## 2. 결론 먼저

**방향은 맞습니다. 다만 세 쌍이 같은 성격이 아닙니다.**

프롬프트를 읽어 보니 `guide` / `apply` / `prayer`는 QT 섹션의 **중복이 아니라, 일부러 다르게
쓰도록 규정된 별도 텍스트**입니다. 셋 중 깨끗하게 재활용되는 것은 **`prayer` 하나**입니다.

| 제안 | QT 쪽 규칙 | infographic 쪽 규칙 | 판정 |
|---|---|---|---|
| summary → guide | **5~6문장**, 높임체 | **2~3문장**, 높임체<br>*"QT summary(5~6문장)보다 짧게 줄여 쓰며, 그대로 복사하지 않는다"* | 길이 2배. **성격 변경** |
| reflection → apply | 3개, **"…생각해봅시다 / 살펴봅시다 / 확인해봅시다"**<br>(성찰 질문) | 2~3개, **평서형 행동 문장**<br>*"✗ …하고 있는지 생각해봅시다. (QT reflection 형식)"* | **정면 충돌** |
| prayer → prayer | **5~6문장**, 경배→회개→감사→간구 | **2~3문장**<br>*"QT prayer(5~6문장)를 잘라 쓰지 않고 따로 작성한다"* | 길이 2배. **가장 무난** |

근거: [prompt_qt_json.go:314-333](../service/prompt_qt_json.go#L314-L333)(필드 규칙),
[:486-503](../service/prompt_qt_json.go#L486-L503)(장년 QT 규칙)

### 2-1. `apply`가 가장 큰 문제입니다

둘은 **길이가 다른 같은 내용이 아니라, 종류가 다른 내용**입니다.

```
QT reflection  "내 섬김이 의무가 아닌 진정한 사랑에서 비롯되는지 살펴봅시다."   ← 자기 점검 질문
infographic    "주의 이름을 부르며 성령의 탄식에 나를 맡긴다."                  ← 오늘 할 행동
```

프롬프트는 이 둘이 섞이는 것을 **명시적으로 금지**합니다. QUALITY CHECKS에도
`✓ apply 항목이 "생각해봅시다/살펴봅시다/확인해봅시다"로 끝나지 않는다`가 들어 있습니다.

섹션 제목도 다릅니다 — QT는 **"깊은 묵상과 적용"**, md는 **"오늘의 적용"**.

### 2-2. 문체가 깨집니다

프롬프트의 문체 규정([:314-316](../service/prompt_qt_json.go#L314-L316)):

```
guide, prayer               : 높임체   (~합니다 / ~습니다)
follow, extra, core, apply  : 평서형 단정 (~한다 / ~이다)
```

`apply`를 reflection으로 바꾸면 md 안에서 **오늘의 적용만 문체가 다른 섹션**이 됩니다.

```markdown
## 말씀을 따라
- 성령께서 우리의 연약함을 도우시며 친히 간구하신다.      ← 평서형

## 오늘의 적용
- 내 섬김이 사랑에서 비롯되는지 살펴봅시다.               ← 혼자 높임체·의문형
```

`guide`와 `prayer`는 원래 높임체라 이 문제가 없습니다.

## 3. 제안이 실제로 해결하는 것 — 생각보다 큽니다

### 3-1. Step2 편집이 md에 반영되지 않는 문제 (현재 버그에 가까움)

9/22 작업으로 Step2 저장 시 md를 다시 쓰게 했지만, 다시 쓸 때 쓰는 값은
`metadata.infographic`에 **박제된 Step1 시점의 guide/apply/prayer**입니다
([qtstep2_service.go](../service/qtstep2_service.go) `rewriteSermonSummary`).

따라서 **Step2에서 말씀의 길잡이나 기도를 고쳐도 md는 바뀌지 않습니다.**
관련 성구·제목·시리즈만 반영됩니다.

재활용하면 이 셋이 Step2 편집 대상에서 바로 오므로 **자동으로 일치합니다.**
이번 제안의 가장 실질적인 이득입니다.

### 3-2. LLM 누락 위험 감소

필드가 6개 → 3~4개로 줄어듭니다. 2026-08-29 테스트에서 5개 모델 중 다수가
`support_scriptures_full`을 통째로 누락했던 전례가 있습니다. **필드가 적을수록 누락이 줄어듭니다.**

`ValidateInfographic`이 실패하면 md가 0바이트가 되므로, 누락 위험 감소는 곧 **md 생성 성공률** 입니다.

### 3-3. 출력 토큰·생성 시간 감소

guide 2~3문장 + prayer 2~3문장 + apply 2~3개를 더 쓰지 않습니다.

## 4. 제안이 바꾸는 것 — 대가

### 4-1. 설교요약문이 길어집니다

`guide` 2~3문장 → 5~6문장, `prayer` 2~3문장 → 5~6문장. **섹션 2개가 2배가 됩니다.**

이 파일은 **인포그래픽 제작 도구에 넣는 문서**이고, 인포그래픽은 지면이 제한적입니다.
짧게 쓰도록 한 규칙은 그 매체를 염두에 둔 것으로 보입니다.

> 다만 이 길이를 다듬는 것은 인포그래픽 제작 단계에서 어차피 하는 일입니다.
> **중복 생성을 없애는 값어치가 더 크다고 판단되면 받아들일 만한 대가입니다.**

### 4-2. 기존 이력의 재작업 결과가 달라집니다

DB에 쌓인 기존 v1.1 이력에는 `guide`/`apply`/`prayer`가 **들어 있습니다.** 새 렌더러가
섹션에서 가져오면 저장된 값은 무시되고, **재작업 산출물이 원래와 달라집니다.**

| 안 | 내용 | 판단 |
|---|---|---|
| 무시 | 항상 섹션에서 가져옴 | 단순. 재작업 결과가 달라짐 |
| 폴백 | `infographic`에 있으면 그것을, 없으면 섹션에서 | 두 포맷을 **영구히** 안고 감 |

→ **무시를 권합니다.** 폴백은 "같은 코드가 이력 나이에 따라 다르게 동작"을 영구화합니다.
그리고 재작업은 **다시 만드는 것**이지 과거 산출물을 복제하는 것이 아닙니다.

## 6. 결정이 필요한 것

### 6-1. `apply`를 재활용할 것인가 — 이 검토의 핵심

| 안 | infographic 필드 | 설명 |
|---|---|---|
| **A. 제안대로** | `follow` `extra` `core` | 최대 축소. **문체가 깨지고 내용 종류가 바뀝니다**(2-1, 2-2) |
| **B. apply 유지** | `follow` `extra` `core` `apply` | guide·prayer만 재활용. 6→4로 33% 축소, 문체 유지 |

**B를 권합니다.** `guide`와 `prayer`는 *같은 내용의 길이 차이*지만, `apply`는 *다른 종류의 내용*
입니다. 성찰 질문("…살펴봅시다")을 "오늘의 적용"에 넣으면 그 섹션의 목적이 바뀝니다.

A를 택하시면 md의 섹션 제목을 **"오늘의 적용" → "깊은 묵상과 적용"** 으로 바꾸는 편이
내용과 맞습니다.

### 6-2. 기존 이력 재작업 (4-2)

→ **무시**를 권합니다.
