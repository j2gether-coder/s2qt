# S2QT 설교 시리즈 수용 검토

작성일: 2026-09-05
배경: 일부 설교가 시리즈물이며, 시리즈명과 설교 제목이 분리되어야 한다
예) 시리즈 `본받고 싶은 교회(1)` / 설교제목 `데살로니가서를 시작하며`
작업 범위: READ ONLY 분석 (코드 변경 없음)

---

## 0. 결론 요약

| 항목 | 판정 |
|---|---|
| 수용해야 하는가 | **예.** 지금은 시리즈를 담을 곳이 없어 제목에 욱여넣는 수밖에 없습니다 |
| 구조적 걸림돌 | **없음.** `metadata`가 `map[string]any`라 필드 추가가 자유롭습니다 |
| DB 스키마 변경 | **불필요** (권장안 채택 시) — 3-3 참조 |
| 예상 공수 | **약 2.5일** (권장안) / 3.5일 (작업내역까지 시리즈 1급 취급) |
| 결정 필요 | **4건** (5장) |

**권장 요지**: 시리즈를 `metadata.series` 한 필드로 추가하고, 화면 입력 → 프롬프트 → temp.json → 산출물까지 **제목과 나란히** 흘려보냅니다. 작업내역 DB는 **스키마를 건드리지 않고**, 목록 라벨에만 시리즈를 합쳐 표시합니다.

## 1. 지금은 어떻게 되는가

현재 시리즈를 담을 자리가 전혀 없습니다. 사용자가 할 수 있는 것은 제목 칸에 `본받고 싶은 교회(1) 데살로니가서를 시작하며`처럼 **합쳐 적는 것**뿐입니다.

그러면 다음 문제가 생깁니다.

| 문제 | 이유 |
|---|---|
| 산출물에서 시리즈와 제목의 시각적 구분이 없다 | `qt-title` 한 줄에 통째로 들어감 ([qtstep2_service.go:354](../service/qtstep2_service.go#L354)) |
| LLM이 시리즈명까지 제목 소재로 오해한다 | 프롬프트가 `{{title}}` 하나만 받고, 비장년은 LLM이 제목을 새로 짓는다 |
| 작업내역에서 같은 시리즈를 묶어 볼 수 없다 | 표기가 사람마다/회차마다 흔들림 |
| 인포그래픽 제목이 길어진다 | `# 본받고 싶은 교회(1) 데살로니가서를 시작하며` |

**필드를 나누는 것이 맞습니다.**

## 2. 다행인 점 — 구조가 이미 열려 있다

### 2-1. `metadata`는 자유 맵이다

`QTSectionDoc.Metadata`가 `map[string]any`입니다([qtstep2_service.go:18](../service/qtstep2_service.go#L18)). 필드를 추가해도 스키마 정의를 고칠 필요가 없고, **모르는 키는 조용히 보존**됩니다.

`support_scriptures_full`이 이미 같은 방식으로 blog 전용 필드로 살아 있습니다.

### 2-2. 작업내역은 이미 원본 JSON을 통째로 보관한다

지난 작업(8/31)에서 `qt_result_json`에 **LLM 원본 전문**을 저장하도록 바꿨습니다. 따라서 `metadata.series`는 **아무 조치 없이 이미 저장·복원됩니다.** 재작업하면 시리즈도 그대로 살아 돌아옵니다.

> 시리즈를 8/31 이전 구조에서 했다면 평면 페이로드(`flatQTStep2Data`)를 함께 고쳐야 했습니다. 지금은 그 작업이 필요 없습니다.

### 2-3. PDF/PNG/템플릿은 HTML 조각을 그대로 렌더한다

새 `<div>`를 추가해도 템플릿 경로가 깨지지 않는지 확인했습니다.

- PDF: `wrapHTMLForPDF(fragment, ...)` — 조각을 그대로 감쌉니다 ([pdf_service.go:853](../service/pdf_service.go#L853))
- 템플릿: `readBaseHTML()` → `wrapHTMLForTemplatePDF(content, ...)` — 마찬가지 ([template_service.go:1092](../service/template_service.go#L1092), [:1011](../service/template_service.go#L1011))

즉 **CSS만 있으면 새 블록이 그대로 표시됩니다.**

> 주의할 곳이 하나 있습니다. `parseQTHTMLToJSON()`이 `qt-title`/`qt-subbox`만 추출하고([pdf_service.go:1371-1372](../service/pdf_service.go#L1371-L1372)), `removeKnownTopLevelBlocks()`도 그 둘만 제거합니다([:1610-1623](../service/pdf_service.go#L1610-L1623)). 새 블록을 추가하면 **이 함수가 만드는 JSON에서는 시리즈가 본문 섹션으로 새어 들어갑니다.**
>
> 다만 이 JSON은 `temp_pdf_source.json`으로 썼다가 **곧바로 삭제되는 부수 산출물**이고([pdf_service.go:840-844](../service/pdf_service.go#L840-L844)), PDF 본체는 조각에서 만들어지므로 **실제 산출물에는 영향이 없습니다.** 그래도 패턴 한 줄을 추가해 두는 편이 안전합니다(공수 거의 0).
>
> 참고로 `SaveHtmlAndMakeJSON()`([:921](../service/pdf_service.go#L921))은 **호출처가 없는 죽은 코드**입니다. 이 함수만 `temp.json`을 직접 덮어쓰므로, 앞으로도 되살리지 않는 편이 좋습니다.

## 3. 손봐야 할 곳

### 3-1. 값이 흘러가는 경로

시리즈는 **사용자 입력**이므로 제목·성구와 같은 길을 탑니다.

```
mainWorkspace.js 기본정보 폼
  → appState.source.basicInfo.series
  → buildLLMRequest()  → QTMeta / LLMPrepareRequest      → 프롬프트 {{series}}
  → SaveManualLLMResult → QTStep1SaveRequest             → temp.json metadata.series
  → LoadQTStep2Data     → QTStep2Data.Series             → Step2 편집 · temp.html
                                                          → blog.html · infographic.md
```

| 파일 | 작업 |
|---|---|
| [frontend/.../mainWorkspace.js:439-469](../frontend/src/components/mainWorkspace.js#L439-L469) | 2열 그리드에 시리즈 입력란 추가 (선택 항목) |
| `frontend/src/state/appState.js` | `basicInfo.series` |
| [frontend/.../bindQTStep1.js:14-28](../frontend/src/components/qt/bindQTStep1.js#L14-L28) | `buildLLMRequest()`에 `series` |

### 3-2. 프롬프트

| 위치 | 작업 |
|---|---|
| `defaultQTPromptJSONSchema` | 스키마 예시에 `"series": "{{series}}"` 추가 |
| 같은 곳 METADATA FIDELITY | `series`를 **입력값 그대로 복사** 목록에 추가 (지어내지 않도록) |
| `BuildQTPromptJSON()` 치환기 | `{{series}}` 추가 |
| 제목 규칙 | **"시리즈명을 제목에 반복하지 않는다"** 한 줄 — 비장년은 LLM이 제목을 새로 짓기 때문에 필요 |

지난 작업에서 METADATA FIDELITY 블록을 이미 만들어 두었으므로 **필드 하나를 목록에 얹는 수준**입니다.

### 3-3. 작업내역 DB — 스키마를 바꾸지 않는 길

`history_master`에는 `series` 컬럼이 없고, **`InitSQLite()`에 `ALTER TABLE` 경로가 전혀 없습니다**([db_service.go:65-114](../service/db_service.go#L65-L114)). 컬럼을 추가하려면 `PRAGMA table_info` 검사 + 조건부 ALTER 기반을 새로 만들어야 합니다(0.5일 이상 + 기존 DB 회귀 위험).

**그럴 필요가 없습니다.** 두 가지 사실 덕분입니다.

1. **시리즈는 이미 저장됩니다.** `qt_result_json`이 원본 전문이므로 `metadata.series`가 그 안에 들어 있습니다. 재작업 복원도 자동입니다(2-2).
2. **`history_master`는 목록 표시·검색용 라벨 테이블**입니다. 진실의 원천이 아닙니다.

따라서 이력 저장 시 `title`에 **시리즈를 합친 라벨**을 넣으면 됩니다.

```go
// service/qtstep1_service.go 의 saveHistory 안
historyTitle := strings.TrimSpace(req.Title)
if s := strings.TrimSpace(req.Series); s != "" {
    historyTitle = s + " — " + historyTitle
}
```

| 얻는 것 | 설명 |
|---|---|
| 목록에 시리즈가 보인다 | `본받고 싶은 교회(1) — 데살로니가서를 시작하며` |
| 시리즈명으로 검색된다 | 기존 키워드 검색이 `hm.title LIKE ?`이므로 그대로 동작 ([history_service.go:303-307](../service/history_service.go#L303-L307)) |
| 제목순 정렬이 시리즈 묶음이 된다 | 시리즈명이 앞에 오므로 자연 정렬됨 |
| DB 변경 0 | 마이그레이션 기반 도입 불필요 |

**한계**: 목록에서 시리즈만 따로 필터링하거나, 회차 숫자로 정렬하는 것은 안 됩니다. 그 요구가 실제로 생기면 그때 컬럼 추가와 마이그레이션 기반을 함께 도입하는 편이 낫습니다(5장 결정 3).

### 3-4. 산출물 렌더링

시리즈를 제목 **위 별도 줄**로 넣는 안을 기준으로 정리합니다.

```html
<div class="qt-wrap">
  <div class="qt-series">본받고 싶은 교회(1)</div>   ← 신규
  <div class="qt-title">[QT] 데살로니가서를 시작하며</div>
```

|---|---|
| [qtstep2_service.go:352-355](../service/qtstep2_service.go#L352-L355) `buildQTStep2HTML` | `qt-series` 블록 (시리즈 없으면 생략) |
| [blog_service.go:127-128](../service/blog_service.go#L127-L128) `buildBlogBody` | 동일 |
| [infographic_service.go](../service/infographic_service.go) `RenderInfographicMD` | `# 제목` 위 또는 아래에 시리즈 한 줄 |
| **CSS 5곳** | 아래 참조 |

**CSS가 이 작업의 실질 비용입니다.** `qt-title` 스타일이 여러 곳에 중복 정의되어 있습니다.

| 파일 | 비고 |

## 5. 확정 사항 (2026-09-05)

| # | 항목 | 결정 |
|---|---|---|
| 1 | **시리즈 표기 방식** | **시리즈 입력란 1칸.** 제목과 분리하되 회차까지 나누지는 않는다. 사용자가 `본받고 싶은 교회(1)`처럼 통째로 입력한다. **비어 있으면 시리즈 기능 자체를 사용하지 않는다**(선택 항목) |
| 2 | **시리즈의 출처** | **사용자 입력 전용.** LLM이 전사문에서 추출하지 않는다 (결정 1의 "비면 미사용"과 정합하며, 날조 위험이 큼) |
| 3 | **작업내역 취급** | **`history_master.title`에 구분자로 합쳐 저장.** `본받고 싶은 교회(1) — 데살로니가서를 시작하며`. **DB 스키마 무변경** (3-3) |
| 4 | **산출물 표시 위치** | **제목 위 별도 줄, 작은 글자.** 신규 `qt-series` 블록 |

```
본받고 싶은 교회(1)              ← qt-series (작은 글자)
데살로니가서를 시작하며            ← qt-title
```

### 결정 2의 보강 — 프롬프트에는 넣되, 값은 신뢰하지 않는다

시리즈명을 프롬프트에 **문맥으로** 넘기면 이득이 있습니다. 비장년은 LLM이 제목을 새로 짓는데, 시리즈 맥락을 알면 더 나은 제목이 나옵니다.

다만 **temp.json에 실리는 값은 화면 입력값으로 덮어씁니다.** LLM 출력을 그대로 쓰지 않으므로 날조가 원천적으로 무의미해집니다. 이는 지난 작업에서 `infographic.md`의 제목·성경본문을 요청값에서 취한 것과 같은 방침입니다.

> 기존 metadata는 "LLM이 준 값을 그대로 둔다"가 원칙이지만, **시리즈는 LLM이 더할 정보가 전혀 없는 순수 사용자 입력**이므로 예외를 둡니다.

### CSS 위치 재확인 (2026-09-05)

`var/template/*`에는 **CSS 파일이 없고 `manifest.json`만 있습니다.** 템플릿은 Go 상수와 `var/conf/*.css`의 스타일을 그대로 물려받습니다. 따라서 손댈 CSS는 4곳입니다.

| 파일 | `.qt-title` 위치 |
|---|---|
| `var/conf/style_qt_html.css` | :54 |
| `var/conf/style_qt_pdf.css` | :62 |
| `service/pdf_service.go` | :323, :692 (테마별 변수는 :293, :458, :494, :616, :665) |
| `service/png_service.go` | :386 |

`var/conf/*.css`가 Go 상수를 덮어쓰는 구조이므로 **양쪽을 함께 갱신**해야 합니다(프롬프트와 같은 이중 관리).

### 7-1. 영향 범위가 좁다 — 경로가 한 곳에만 있다

|---|---|
| `util/path.go` | **문자열 2개** — 실질 변경은 여기가 전부 |
| 주석·로그 문구 | 20여 곳. 기능 영향 없으나 정확도를 위해 함께 정리 |
| `.gitignore` | **없음** — `/var/temp/` 전체가 무시됨 |
| 프론트엔드 | **없음** — `result.blog.filePath`처럼 경로를 값으로 받음 |
| `SaveGeneratedFile` | **없음** — `formatKey`로 확장자만 정함([file_service.go:357](../service/file_service.go#L357)) |
| `var/doc/user_guide.md` | **없음** — 두 파일을 언급하지 않음 |

### 7-2. 이전 이름의 파일 정리 — 기존 장치를 쓴다

`AppPaths.LegacyTempFiles`가 이미 있습니다([util/path.go:60-62](../util/path.go#L60-L62)). 예전 `video.mp4`를 정리하려고 만든 것으로, **새 작업 시작 시 자동 삭제**됩니다([pipeline_service.go:46](../service/pipeline_service.go#L46)).

여기에 `blog.html`과 `infographic.md`를 추가하면 남은 파일이 저절로 정리됩니다. **새 장치를 만들 필요가 없습니다.**

> 사용자가 이전 `infographic.md`를 편집해 두었다면 새 작업 시작 시 삭제됩니다. 다만 그 시점은 **다른 설교를 시작하는 때**라 이미 무의미한 파일이므로 문제되지 않습니다.

### 7-3. 코드 식별자까지 고칠 것인가

파일만 바꾸고 코드가 계속 `Blog`라고 부르면, **개발자가 실제로 읽는 자리에 오해가 남습니다.** 범위를 3단계로 나눠 봤습니다.

| 단계 | 범위 | 추가 공수 |
|---|---|---|
| 1 | 파일명 2개 + `LegacyTempFiles` + 주석·로그 문구 | 0.2일 |
| 2 | 1 + 경로 상수 (`TempBlog`→`TempExtendedHtml`, `TempInfographic`→`TempSermonSummary`) | +0.1일 |
| 3 | 2 + 결과 필드·서비스 (`QTStep3Result.Blog`→`Extended`, `BlogService`→`ExtendedService`, `blog_service.go` 파일명) | +0.2일 |

**단계 3까지 권장합니다.** 각 조각이 작고(결과 필드는 3곳, 프론트 1줄), 이름을 고치는 작업의 목적 자체가 오해 제거이기 때문입니다.

다만 **`infographic`이라는 말은 코드에 남겨야 합니다.** LLM 출력 JSON의 필드명이 `infographic`이고(프롬프트 계약), `InfographicData`·`ValidateInfographic`은 그 데이터를 가리킵니다. **바뀌는 것은 "그 데이터를 렌더한 산출물 파일"의 이름뿐**입니다.

```
infographic (JSON 필드·타입)  → 그대로 유지
sermon_summary.md (산출물)    → 이름 변경
```

### 7-4. 공수

**단계 3 기준 0.5일.** 시리즈 작업(2.5일)과 합쳐 **약 3.0일**입니다.

파일명 변경은 시리즈 작업과 **의존 관계가 없으므로** 먼저 하든 나중에 하든 무방합니다. 다만 `RenderInfographicMD` 시그니처를 어차피 손대므로(시리즈 인자 추가), **함께 진행하면 같은 파일을 두 번 열지 않습니다.**
